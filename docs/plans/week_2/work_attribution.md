## Work Attribution

Follow-on to `observ_improvements.md`, which landed provenance on tool calls.

In the session log I can now see **Automatic context work**, and inside it I can
see `room survey` and the tool calls it made. What I still cannot see:

- the cost of our custom local model — the one that picks look candidates;
- the writes that were performed to the database;
- `room_survey` as its own expandable group *nested under* automatic context
  work, rather than a label repeated on four sibling calls.

So we need more logging calls, and better grouping of related work.

## Technical Solution

### 0. What already exists, and what is actually missing

Three corrections to the framing, because they change the size of the work:

**The custom model is not in `RoomParser`.** `Mud::RoomParser` is pure text →
struct and deliberately has no round trips of any kind. The 41M-parameter ONNX
token classifier is `Extractors::Model`, assembled into a plain lambda by
`Extractors.look_candidates` and injected into `Mud::RoomSurvey`, which calls it
once per newly-discovered room from `#candidates`. It is completely unlogged
today: not its ~10ms, not whether the weights were even installed, not how many
candidates it kept out of how large a pool. A room record can carry a
`look_candidates` field produced by a model that silently degraded to `Null` and
nothing in the session says so.

**The database writes ARE logged — to a different file.** `Memory::Store` emits
generic CDC through `Journal` on every mutation (`jupsert` for keyed values,
`jevent` for discrete ops), landing in `.boukensha/journal/<date>.jsonl` and
rendered by the Progression tab. Every record already carries `session_id`,
`at`, `mono_ms` and `seq`. So the data exists; what is missing is a **join** —
nothing connects "the survey wrote 3 entities and 4 exits" to the survey in the
session transcript.

That join cannot be done on time windows alone and cannot be done from the
journal alone either, for one reason worth stating plainly: `jupsert` is
change-detecting by design, so a write of an unchanged value appends nothing. A
survey that re-reads a room it already knows performs real database work and
produces zero journal lines. "How much did we write" and "what changed" are
different questions, and only the second one has an answer on disk today.

**The grouping is inferred, not recorded.** `buildTranscriptTree` folds *runs of
adjacent* hook-initiated tool calls into one group, then sub-groups them by the
`operation` string. Adjacency is a proxy for containment, and it is wrong in
both directions: a model call landing between two hook calls splits one logical
operation into two groups, and `room_survey`'s calls sit as siblings of
`position_refresh`'s when the survey actually runs *inside* it (`before_model` →
`resolve_position` → `discover` → `@survey.survey`). The log records a flat
label where the truth is a tree.

All three of these are the same missing concept: **a unit of work is not an
event in this log.** Everything is instantaneous — a call, a result, a
transform. Nothing says "here is a thing that started, contained other things,
and finished, having spent this much of what."

### 1. Operation spans as first-class events

Give the logger a span, the way it already has a task bracket:

```ruby
def operation(name, trigger: nil, &block)
```

It writes an `operation_start`, yields, and writes an `operation_end` carrying
the duration and the rollups accumulated inside it:

```json
{ "phase": "operation_start", "operation_id": "op_4f21a0",
  "parent_operation_id": "op_9c1e33", "operation": "room_survey",
  "trigger": "before_model", "task": "player", "depth": 0 }

{ "phase": "operation_end", "operation_id": "op_4f21a0",
  "operation": "room_survey", "duration_ms": 1240,
  "mud_calls": 4, "mud_ms": 1180,
  "db_reads": 6, "db_writes": 11, "db_ms": 3,
  "inference_ms": 11, "journal_lines": 7, "ok": true }
```

`operation_id` is generated by the logger and returned, exactly as `call_id` is,
and it is what everything else correlates on. `parent_operation_id` is the span
below it on the stack, which is what makes the nesting a fact rather than a
guess about adjacency.

**The stack lives where two writers can both read it.** `Logger` already stamps
`task`/`depth` on every event from a stack it owns, and its own comment explains
why: *"a field a call site can forget is a field that goes dead."* The same
argument applies here and is stronger, because there are now two writers —
`Logger` and `Journal` — that must agree on which operation is current. So the
stack goes in one small ambient holder both consult:

```ruby
module Boukensha
  module Operation      # thread-local; nil when no span is open
    def self.current = ...
    def self.push(id) / pop
  end
end
```

Ambient state is a real cost and worth naming: it is invisible at the call site
and it is per-thread, so a future concurrent agent gets correct isolation but a
future *fiber* scheduler would not. The alternative — threading an
`operation_id:` argument through `Logger`, the dispatcher, `RoomSurvey`, `Store`
and `Journal` — is the shape we already have for `operation:` after
`observ_improvements.md`, and it has one call site per hop that can forget it.
The ambient version is the one that cannot go dead.

**This deletes plumbing rather than adding it.** With the ambient stack,
`Boukensha.tool_dispatcher`'s third `meta` argument, `Mud::Hooks#call_meta`,
`Mud::Hooks#during` and `RoomSurvey`'s `call_meta:` constructor parameter all
go away: the dispatcher stamps `initiator: "hook"` and the logger fills
`operation`/`operation_id` from the span it is inside. `Mud::Hooks` calls
`@logger.operation("room_survey", trigger: "before_model") { ... }` and the
label reaches the log without being passed anywhere.

Spans to open, and where:

| span | opened in | contains |
|---|---|---|
| `player_bootstrap` | `before_turn` | `check(score)` |
| `async_poll` | `before_tools` | `poll` |
| `position_refresh` | `before_model` | `look`, and everything below |
| `room_disambiguation` | `disambiguate` | `check(exits)` |
| `room_survey` | `RoomSurvey#survey` | `look`, `check(exits)`, `consider`, `examine`, one inference |
| `state_render` | `before_model` | the store reads behind the `[here]` block |

`room_survey` opens in `RoomSurvey#survey` rather than in the hook that calls
it, so the span is the survey's own property and a second caller could not
mislabel it.

Every `tool_call` gains `operation_id` alongside the `operation` string it
already has. The string stays because it is human-readable and survives a log
whose spans were truncated mid-write; the id is what the tree is built from.

### 2. Log the local model's cost

`Extractors.look_candidates` is the only place that holds both the model and the
knowledge of what it just did, so the timing goes there — wrapped around the
lambda it already returns, with `logger:` passed from the entrypoint the same
way `Mud::Hooks` gets it:

```json
{ "phase": "local_inference", "operation_id": "op_4f21a0",
  "model": "look_candidates", "backend": "onnx",
  "artifact": "models/look_candidates/model.onnx",
  "duration_ms": 11, "pool": 23, "kept": 3,
  "threshold": 0.62, "top_k": 5,
  "cost_usd": 0.0, "unit": "local", "available": true }
```

Four fields carry their weight beyond the timing:

- `available: false` is the one that matters most. A missing artifact degrades
  to `Model::Null`, which warns **once** to stderr and then returns `[]`
  forever. Nothing in the session log says the field is empty because the model
  is absent rather than because the room had nothing worth looking at — and
  those are opposite conclusions when you are deciding whether the extractor
  earns its probes.
- `pool` and `kept` are the yield. `look_candidates` exists to be A/B-ed
  (`extractor: none` is a documented setting for exactly that), and "23
  candidates scored, 3 kept" is the number that argues for or against it.
- `threshold`/`top_k` come from the artifact's `manifest.json`, never from
  settings, precisely so they travel with the weights they were measured on.
  Logging them per call means a room record can be explained by the calibration
  that produced it after a retrain has moved on.
- `cost_usd: 0.0` with `unit: "local"` is deliberately explicit rather than
  omitted. The cost table currently has no row for this model at all, which
  reads as "no cost information" when the truth is "free, and here is the
  latency it cost instead". Three LLM calls used to do this job; saying $0 out
  loud is the measurement that replaced them.

The ~110ms one-time graph load is separate and belongs on the `session_start`
snapshot, not on a per-room event that would report it once and mislead about
the steady state.

### 3. Instrument the store, and stamp the journal

**Counters, not statements.** Every SQL statement as its own transcript entry
would bury the narrative under ~20 rows per survey to answer a question nobody
asks per-statement. What is wanted is the shape of the work: this operation read
6 rows and wrote 11, in 3ms.

`Memory::Store` funnels through `@db` in 26 `execute` calls plus `transaction`
and `last_insert_row_id`, so one counting proxy at construction covers all of
them without touching a single query:

```ruby
# Wraps the SQLite3 handle, counts execute() by statement kind, and forwards
# everything else (get_first_value, transaction, last_insert_row_id) untouched —
# `Store#db` is public and the tests reach through it.
class CountingDb
  def execute(sql, *rest) = count(sql) { @db.execute(sql, *rest) }
  def method_missing(name, *args, &blk) = @db.send(name, *args, &blk)
end
```

Read vs write is the leading SQL keyword; `PRAGMA` and the `Schema.migrate!`
statements run before the wrap and are not counted, which is correct — they are
boot, not work.

The span reads the counters at open and close and reports the delta. That is
strictly cheaper than a callback per statement and it cannot double-count a
nested span, because a delta over an interval is exactly what nesting means.

**The journal gets the same `operation_id` stamp.** `Journal#write` already
merges reserved keys over caller fields; adding `operation_id` from
`Boukensha::Operation.current` means every CDC line knows which unit of work
produced it, and the monitor joins journal detail into a span by id — no
mono_ms window, no midnight-rotation edge case to reason about, no possibility
of attributing a write to the wrong operation because two spans were 4ms apart.

`journal_lines` on `operation_end` is then a *cross-check*, not a duplicate: if
a span reports `db_writes: 11, journal_lines: 7`, four writes were no-ops the
journal correctly swallowed, and the difference is itself the interesting
number — it is how you find a survey re-writing values that never change.

To serve the join, `/api/v1/journal` gains an `operation_id=` (and `session=`)
filter. Nothing new is written, nothing is duplicated; the existing change log
becomes addressable by unit of work.

### 4. Monitor: real nesting, and a rollup per span

The transcript tree stops inferring and starts reading. `buildTranscriptTree`
gains a third node kind built from `operation_start`/`operation_end` and
`parent_operation_id`, so the shape the user asked for falls out of the data:

```text
▾ Automatic context work · 4 operations · 2.4s
  ▸ bootstrap player      check(score)                  1.93s
  ▾ establish position                                  0.42s
      ▸ room survey       look, check(exits), consider…  0.31s
          ⚙ tbamud__look                                0.10s
          ⚙ tbamud__check(exits)                        0.09s
          ⚙ tbamud__consider(cityguard)                 0.06s
          ⚙ tbamud__examine(cityguard)                  0.06s
          ◆ look_candidates · 23 scored → 3 kept · 11ms · local, $0
          ⛁ wrote 11 · read 6 · 3ms   (7 journal lines)
      ⚙ tbamud__look                                    0.10s
  ▸ poll × 8, all empty                                 0.04s
```

Rules that keep it honest, carried forward from the previous plan and extended:

- A span whose `operation_end` never arrived renders **incomplete** rather than
  implying it finished, the same treatment `task_end` already gets.
- A failed call, or a non-empty `poll`, still force-expands its ancestors. Being
  nested must never make something harder to notice than being flat did.
- The `⛁` and `◆` rows are summaries of the span, not entries in the narrative,
  and they collapse with it.
- The journal detail behind `7 journal lines` is fetched lazily on expand, not
  bundled into the session payload. The session view should not grow a second
  full log inside it.
- A log with no spans renders exactly as it does today. `operation_start` is
  additive and every file already on disk lacks it.

Session summary gains `operations`, `db_writes`, `db_reads` and
`local_inference_ms`, and the cost table gains a `local / look_candidates` row
priced at $0 with its call count and total latency — so "what did this session
spend" answers in dollars *and* in the two currencies that are not dollars.

---

### 5. What this deliberately does not do

- **No per-statement SQL log.** Counters and the existing CDC cover the
  questions being asked; a statement log answers a question about the store,
  which is `test_memory_store.rb`'s job.
- **No duplication of journal content into the session log.** One writer per
  fact. The session log gets counts and an id; the journal keeps the detail.
- **No timing of `RoomParser`.** It is pure string work in the hot path of
  `after_tool`; instrumenting it would cost more than it measures.
- **No new streaming infrastructure.** The journal filter is a query parameter
  on an endpoint that already streams under the same 8-slot `StreamGate`.

---

### Implementation order

1. **`Boukensha::Operation` + `Logger#operation`** — spans, ids, and the
   nesting. Then delete the `meta`/`call_meta` plumbing the previous plan added,
   since the ambient stack replaces it. Parser-side: read spans, keep the
   adjacency fallback for existing logs.
2. **`local_inference`** — smallest independent win, and the only one that can
   reveal a silently-absent model. Includes the `available: false` path, which
   deserves a test with no artifact on disk.
3. **Store counters** — the `CountingDb` proxy and the span delta. Verify
   `Store#db` still satisfies `test_memory_store.rb` through `method_missing`.
4. **Journal `operation_id` + the API filter** — the join, once there are ids to
   join on.
5. **Monitor nesting and rollups** — last, because it is a renderer over
   everything above, and each of 1–4 is independently observable in the raw
   JSONL before any of this exists.

### Acceptance criteria

- `room_survey` renders as an expandable group nested inside
  `establish position`, inside **Automatic context work** — three levels, from
  `parent_operation_id`, not from adjacency.
- A model tool call landing between two hook calls no longer splits one
  operation into two groups.
- Every newly-discovered room shows one `look_candidates` row with its latency,
  pool size, kept count, and `$0`; a checkout with no artifact shows the same
  row reading `unavailable` instead of showing nothing.
- Each span reports rows read and written, and the journal lines it produced,
  with the gap between writes and journal lines visible rather than implied.
- Expanding a span's journal detail loads it on demand and shows the same lines
  the Progression tab shows for that operation.
- A session file written before this plan renders exactly as it does now.
- An operation interrupted mid-flight is labelled incomplete, and a failed or
  non-empty automatic call is still never hidden by default.
